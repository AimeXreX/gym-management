# چرخه کامل مربی و عضو (Coach ↔ Member)

> وضعیت: **کامل** — فاز ۱ تا ۷ پیاده‌سازی شده و چرخه کامل باشگاه (انتساب → درخواست → برنامه → اجرا → پیشرفت → بازبینی) بسته است.
> مرتبط با: ADR 0010 (wellness و انتساب مربی)، و ADR جدید 0011 برای «درخواست مربی/برنامه» و «برنامه تمرینی آینده‌نگر».

## هدف

بستن حلقه کامل باشگاه در حوزه مربی/عضو:

```
مدیر/مالک، مربی پیش‌فرض هر عضو را تعیین می‌کند
        ↓
عضو می‌تواند درخواست «مربی» یا «برنامه» بدهد
        ↓
مربی (پیش‌فرض یا منتخب) برنامه تمرینی/غذایی می‌نویسد
        ↓
عضو برنامه را می‌بیند، اجرا و پیشرفت را ثبت می‌کند
        ↓
مربی پیشرفت را می‌بیند و برنامه را به‌روز می‌کند (بازخورد)
```

## وضعیت فعلی (چه چیزی داریم)

- `coaches` + `members` + `coach_member_assignments` (دامنه‌ی `training`/`nutrition`، فقط سیدر می‌سازد).
- ماژول `wellness` (وابسته به `members`, `coaches`, `attendance`): `NutritionPlan`/`NutritionPlanItem`، `WorkoutSession`/`WorkoutSet`، `FoodLog`، `BodyMeasurement`، `InjuryRecord`، `ProgressPhoto`.
- `WellnessAccess`: مجوزهای record-level (`canView`, `canCoach`, `canCoachDomain`).
- اتصال مربی به حساب ورود از طریق `coaches.user_id` (منحصر به `[gym_id, user_id]`).
- `coach_type`: `training`/`nutrition`/`both` (به تازگی در UI و اعتبارسنجی تکمیل شد).

## شکاف‌های اولیه (همگی در فاز ۱ تا ۵ بسته شدند)

1. **انتساب مربی↔عضو UI ندارد.** `CoachMemberAssignment` فقط در `DatabaseSeeder` ساخته می‌شود؛ نه روت، نه کنترلر، نه فرم. مدیر نمی‌تواند مربی را به عضو متصل کند.
2. **مربی پیش‌فرض وجود ندارد.** هیچ مکانیزمی برای علامت‌گذاری «مربی اصلی/پیش‌فرض» یک عضو وجود ندارد.
3. **انتخابگر شاگرد ندارد.** در `WellnessController::index` مربی فقط `->first()` عضو منتسب را می‌بیند؛ برای بقیه باید دستی `/wellness/{member_id}` بزند و هیچ لیست/لینکی برای جابه‌جایی بین شاگردها ندارد.
4. **عضو نمی‌تواند درخواست بدهد.** هیچ مسیری برای «درخواست مربی» یا «درخواست برنامه» از سمت عضو نیست.
5. **برنامه تمرینی آینده‌نگر ندارد.** `WorkoutSession` فقط «رکورد جلسه‌ی اجراشده» است؛ معادلِ «برنامه غذایی» (که آینده‌نگر است) برای تمرین وجود ندارد.
6. **لینک اشتباه در پروفایل مربی.** اعضای منتسب در صفحه مربی به `members.show` لینک شده‌اند نه به `/wellness/{member}`.
7. **حلقه بسته نیست:** نه اعلان برای درخواست/تأیید، نه نمای پیشرفت برای مربی، نه بازخورد برنامه.

## فازها

### فاز ۱ — انتساب مربی↔عضو + مربی پیش‌فرض (زیرساخت) ✅

- مهاجرت: افزودن `is_default` به `coach_member_assignments` (حداکثر یک پیش‌فرض به ازای هر `member_id`+`domain`).
- روت/کنترلر/اکشن: انتساب (`assign`)، حذف (`unassign`)، فعال/غیرفعال، و علامت‌گذاری پیش‌فرض (`setDefault`).
- UI ادمین: در صفحه‌ی عضو، بخش «مربی‌های منتسب» — افزودن مربی (با انتخاب دامنه)، حذف، و انتخاب پیش‌فرض.
- مجوز: `gym.manage` برای تغییر؛ مشاهده برای مدیر/مالک.
- لینک اعضای منتسب در پروفایل مربی → اصلاح به `/wellness/{member}`.

### فاز ۲ — انتخابگر شاگرد برای مربی ✅

- در `/wellness` برای مربی، یک انتخابگر اعضای منتسب (دراپ‌داون/لیست) با لینک به `/wellness/{member}`.
- حفظ عضو جاری در کوئری‌استرینگ/سشن تا جابه‌جایی روان باشد.
- مربی فقط اعضای منتسب خودش را می‌بیند (fail-closed).

### فاز ۳ — برنامه تمرینی آینده‌نگر (Workout Program) ✅

- مهاجرت: `workout_programs` + `workout_program_days` + `workout_program_sets` (ساختار شبیه nutrition plan، با نویسنده = مربی تمرین).
- کنترلر/اکشن: ایجاد، ویرایش، آرشیو برنامه؛ مربی تمرین (یا عضو برای خودش) می‌نویسد.
- نمایش: عضو و مربی، برنامه‌ی فعال را می‌بینند؛ رکورد اجرا (`WorkoutSession`) به برنامه لینک می‌شود.
- ADR 0011: تفاوت «برنامه» (آینده‌نگر) و «رکورد جلسه» (اجراشده).

### فاز ۴ — درخواست مربی/برنامه از سمت عضو ✅

- مهاجرت: `coach_requests` — `member_id`, `coach_id?` (خالی = هر مربی/پیش‌فرض), `domain`, `type` (`assign`|`program`), `message`, `status` (`pending`|`approved`|`rejected`), `reviewed_by`, `reviewed_at`.
- کنترلر/اکشن: عضو درخواست می‌دهد؛ مربی/ادمین تأیید یا رد می‌کند؛ تأیید `assign` → ساخت `coach_member_assignment`.
- UI عضو: فرم درخواست در `/wellness` + نمایش وضعیت درخواست‌ها.
- UI مربی/ادمین: صندوق درخواست‌ها + دکمه تأیید/رد.
- اعلان به طرف مقابل (ادغام با ماژول `notifications` موجود).
- ADR 0011: جریان درخواست و قواعد (چه کسی می‌تواند تأیید کند، انقضا، منحصربه‌فرد بودن درخواست باز).

### فاز ۵ — بستن حلقه (بازخورد و پیشرفت) ✅

- نمای پیشرفت عضو برای مربی (آخرین وزن، تعداد برنامه‌ها/جلسات/حضور در یک ردیف آمار).
- بازخورد روی برنامه از طریق `notes` برنامه‌ها/جلسات (فاز ۳).
- اعلان‌های چرخه: درخواست جدید، تأیید/رد، ساخت برنامه توسط مربی، انتشار برنامه (`workout_program.published`).
- جدول `notifications` (tenant-scoped) + کنترلر/روت + زنگوله سربرگ + صفحه اعلان‌ها.
- تکمیل چرخه: برنامه → اجرا → پیشرفت → بازبینی برنامه.

## تکمیل‌های پس از فاز ۵ (خارج از نقشه اولیه) ✅

پس از بستن حلقه، این موارد هم برای کامل‌شدن تجربه مربی/عضو اضافه شد:

### بررسی درخواست توسط خود مربی
- `CommercialWorkflows::canReviewCoachRequest`: زنجیره تأیید/رد «مربی هدف → مربی پیش‌فرض دامنه → `gym.manage`».
- صندوق مربی (`/coach-requests`) + دکمه تأیید/رد در صفحه عضو؛ روت بررسی بدون `gym.manage` و با مجوز record-level.

### داشبورد مربی
- `GET /coach-dashboard` (`wellness.dashboard`): کارت آمار + کلاس‌های امروز + درخواست‌های باز + فهرست «شاگردان من» (با آخرین وزن و برنامه فعال).
- مربی بعد از ورود مستقیم به داشبورد می‌رود؛ عضو همچنان به `/wellness`.

### تکمیل پرونده مربی (سمت مدیر)
- فیلدهای `biography`، `hire_date`، `compensation_notes` و اتصال حساب ورود (`user_id`) به فرم ایجاد/ویرایش مربی.
- `user_id`: کاربر باید عضو فعال همان باشگاه باشد و هر کاربر حداکثر به یک مربی در هر باشگاه متصل شود.
- `compensation_notes` فقط برای مدیر/مالک در پروفایل مربی نمایش داده می‌شود.

### مشخصات بدنی و پیشرفت عضو
- فیلد `height_cm`/`weight_kg` (قد/وزن پایه) به فرم عضو و اعتبارسنجی.
- پروفایل عضو (`members.show`): کارت «مشخصات بدنی»، «اندازه‌گیری‌های اخیر»، «نمودار پیشرفت وزن» و «تصاویر پیشرفت».
- عکس‌های پیشرفت: فقط `visibility=coaches` برای مدیر/مالک؛ `private` هرگز به مدیر/کارمند نمایش داده نمی‌شود؛ کارکنان کارت تصاویر را نمی‌بینند.
- نمودار وزن به کامپوننت قابل استفاده مجدد `<x-weight-chart>` تبدیل شد (مشترک بین `/wellness` و `members.show`).

## فاز ۶ — کامل‌سازی تجربه مربی ✅

شش شکاف باقی‌مانده از تجربه مربی، به ترتیب، همه بسته شدند:

### ۶-۱ — ویرایش برنامه‌ها ✅
- `GET/PUT /wellness/programs/{program}/edit` و `GET/PUT /wellness/plans/{plan}/edit`.
- `CommercialWorkflows::updateWorkoutProgram` (جایگزینی روزها/ست‌ها در تراکنش) و `updateNutritionPlan` (جایگزینی آیتم‌ها).
- مجوز: مربی منتسبِ دامنه یا عضوِ صاحبِ برنامه (برنامه شخصی بدون مربی).

### ۶-۲ — پیگیری اجرای برنامه ✅
- فرم «ثبت رکورد جلسه» حالا روز برنامه را اختیاری می‌پذیرد (`program_day_id` → `program_id`).
- نمایش بج «اجرا شده» روی هر روز برنامه که جلسه‌ای به آن لینک شده است.

### ۶-۳ — تقویم کلاس‌های مربی ✅
- در داشبورد مربی، بخش «کلاس‌های پیش رو (۷ روز آینده)» با ساعت، شعبه و ثبت‌نام.

### ۶-۴ — پروفایل خود مربی ✅
- روت/صفحه `wellness.profile` برای مشاهده و ویرایش تخصص، موبایل، ایمیل، بیو و آواتار خود مربی.

### ۶-۵ — بازخورد روی برنامه ✅
- جدول `workout_program_feedback` (tenant-scoped) + نظرات مربی/عضو روی برنامه تمرینی (owner یا مربی تمرینِ منتسب).

### ۶-۶ — اعلان کلاس‌ها ✅
- `CommercialWorkflows::notifyClassSession`: اعلان به مربی هنگام ساخت (`scheduled`) یا لغو (`cancelled`) جلسه کلاس او.

## فاز ۷ — کتابخانه تمرین و قالب‌های قابل استفاده مجدد ✅

مربی بتواند یک‌بار تمرین‌ها را ذخیره کند و به چند شاگرد اختصاص دهد (مثل «ست پیش‌فرض» یا «هوازی ماه اول/دوم»):

### ۷-۱ — کتابخانه تمرین (`exercises`)
- جدول gym-scoped با `name`, `category` (`strength`/`cardio`/`stretching`), `muscle_group`, `equipment`, `description`, `created_by`.
- مشترک در کل باشگاه؛ مربی تمرین یا مدیر می‌سازد.

### ۷-۲ — قالب برنامه (`workout_templates`)
- `workout_templates` (نام، هدف، یادداشت، `coach_id` nullable = قالب شخصی یا باشگاهی) + `workout_template_days` (فاز «ماه اول/دوم» + روز) + `workout_template_sets` (`exercise_id` + نام حرکت + وزنه/تکرار/مدت هوازی).
- مربی تمرین قالب خودش را می‌سازد؛ مدیر می‌تواند قالب باشگاهی (`coach_id = null`) بسازد.

### ۷-۳ — اختصاص قالب به شاگردان
- `assignWorkoutTemplate`: قالب را برای یک یا چند عضو انتخاب می‌کند و برای هر عضو یک `workout_program` واقعی (روزها/ست‌ها کپی می‌شود، فاز در عنوان روز حفظ می‌شود) می‌سازد + اعلان به عضو.
- مجوز: مربی تمرین فقط برای شاگردان منتسب خودش؛ مدیر برای هر عضو.

## قواعد غیرعملکردی (الزامی از AGENTS.md)

- **Tenancy fail-closed:** هر جدول جدید `gym_id` دارد و فقط از مسیر `BelongsToGym`/Scope مرکزی خوانده می‌شود.
- **سه کنترل مستقل:** module (wellness/coaches) + role (`gym.manage`, مربی، عضو) + permission — هیچ‌کدام جای دیگری را نمی‌گیرد.
- **Controller نازک:** منطق در Action/Service؛ Query پیچیده در Query Object.
- **Core ↔ ماژول تجاری ممنوع:** API داخلی ماژول صریح بماند.
- **ADR:** فاز ۳ و ۴ → ADR 0011 (قبل از نوشتن کد مهاجرت).
- **تست:** unit (دامین‌ریول: انتساب/پیش‌فرض/درخواست/مجوز) + feature (جریان HTTP + جداسازی cross-gym) + architecture (هر مدل جدید tenant-scoped).

## ترتیب اجرا

1. فاز ۱ (زیرساخت انتساب + پیش‌فرض + اصلاح لینک) — مسدودکننده‌ی بقیه.
2. فاز ۲ (انتخابگر شاگرد) — بعد از ۱، کوچک و مستقل.
3. فاز ۳ (برنامه تمرینی) — به ADR 0011 نیاز دارد.
4. فاز ۴ (درخواست مربی/برنامه) — به ADR 0011 نیاز دارد.
5. فاز ۵ (بازخورد/پیشرفت/اعلان) — بستن حلقه.

- UI فارسی/RTL و ترجمه‌پذیر.
- تست‌ها سبز (SQLite + MySQL).
- اسکوپ tenancy fail-closed (IDOR → 404/403).
- ADR به‌روز.
