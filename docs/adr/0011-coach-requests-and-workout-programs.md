# ADR 0011 — درخواست مربی/برنامه و برنامه تمرینی آینده‌نگر

## وضعیت

پذیرفته‌شده — 2026-08-17 (پیاده‌سازی‌شده در فاز ۳ و ۴ از `docs/coach-member.md`؛ چرخه مربی/عضو کامل شد)

## زمینه

ADR 0010 انتساب مربی↔عضو و پرونده wellness را پایه‌گذاری کرد، اما دو شکاف باقی ماند:

1. **برنامه تمرینی فقط «رکورد جلسه» است.** `WorkoutSession` یک جلسه‌ی اجراشده را ثبت می‌کند؛ معادلِ آینده‌نگری که `NutritionPlan` برای تغذیه دارد، برای تمرین وجود ندارد.
2. **عضو هیچ مسیری برای درخواست ندارد.** انتساب فقط از سمت مدیریت انجام می‌شود؛ عضو نمی‌تواند درخواست مربی یا برنامه بدهد و مربی فقط برای اعضای از قبل منتسب برنامه می‌نویسد.

با فاز ۱، «مربی پیش‌فرض» (`coach_member_assignments.is_default`) اضافه شد و حالا می‌تواند مقصد درخواست‌های بدون مربیِ مشخص باشد.

## تصمیم

### ۱) برنامه تمرینی آینده‌نگر (Workout Program)

- «برنامه» از «رکورد جلسه» جدا است: `workout_programs` آینده‌نگر است و `workout_sessions` اجرای واقعی را ثبت می‌کند.
- ساختار سلسله‌مراتبی: `workout_programs` → `workout_program_days` (روز/عنوان) → `workout_program_sets` (حرکت، ست، وزنه، تکرار).
- نویسنده، مربی تمرینِ منتسب در دامنه `training` (یا خود عضو برای برنامه شخصی) است؛ مربی منتسب می‌تواند ویرایش کند و عضو فقط می‌خواند (همان الگوی ADR 0010 برای `nutrition_plans`).
- چرخه‌ی وضعیت: `draft` → `active` → `completed`/`archived`؛ تاریخچه با status نگه داشته می‌شود، نه حذف.
- `workout_sessions.program_id`/`program_day_id` (nullable) اجرا را به برنامه لینک می‌کند تا پیشرفت قابل ردیابی باشد.

### ۲) جریان درخواست مربی/برنامه (Coach Request)

- عضو می‌تواند درخواست `assign` (مربی) یا `program` (برنامه) بدهد؛ مقصد می‌تواند مربی مشخص یا خالی (مربی پیش‌فرض / هر مربیِ دامنه) باشد.
- جدول `coach_requests`: `member_id`, `coach_id?`, `domain`, `type`, `message`, `status`, `reviewed_by`, `reviewed_at`.
- فقط **یک درخواست باز (`pending`)** به ازای هر `member_id + domain + type` مجاز است (جلوگیری از اسپم و درخواست‌های موازی).
- تأیید `assign` → ساخت `coach_member_assignment` با همان قواعد فاز ۱ (`coach_type`/دامنه، فعال بودن مربی). تأیید `program` برنامه را خودش نمی‌سازد؛ فقط به مربی اجازه/اعلام می‌دهد که برنامه بنویسد.
- تأیید/رد توسط: مربی هدف (اگر `coach_id` مشخص باشد)، وگرنه مربی پیش‌فرض دامنه، وگرنه `gym.manage`. رد باید دلیل داشته باشد و عضو نتیجه را ببیند.

### ۳) قواعد مشترک

- هر جدول جدید `gym_id` دارد و فقط از مسیر Scope مرکزی fail-closed خوانده می‌شود؛ دسترسی record-level مشابه `WellnessAccess`.
- سه کنترل مستقل: module (`wellness`) + role (`member`/`coach`/`manager`) + record-level — هیچ‌کدام جای دیگری را نمی‌گیرد.
- Controller نازک؛ منطق در Action/Service و Query پیچیده در Query Object.
- اعلان درخواست/تأیید/رد از ماژول `notifications` موجود استفاده می‌کند؛ سیستم اعلان جدید ساخته نمی‌شود.

## خارج از دامنه فعلی

- چت بلادرنگ، پیام‌رسانی، تماس ویدیویی و اپ موبایل مربی/عضو.
- تولید خودکار یا هوشمند برنامه (AI).
- فروش برنامه‌ی پولی یا درگاه پرداخت (در صورت نیاز ADR جداگانه).

## پیامدها

- داده‌ی تمرین دو لایه می‌شود (برنامه + رکورد اجرا) و باید در گزارش‌ها و UI جدا دیده شود.
- جریان درخواست یک state machine ساده (`pending`/`approved`/`rejected`) اضافه می‌کند که باید در audit ثبت شود و با قواعد `assignCoach` سازگار بماند.
- مربی پیش‌فرض به یک نقطه‌ی تحویل واقعی تبدیل می‌شود؛ بدون آن، درخواست‌های بدون مربی باید توسط `gym.manage` مدیریت شوند.
